01

The honest read

Enterprise-Agent is a genuinely well-designed orchestration skeleton — human approval gates at every risky step, least-privilege connectors, an audit trail, a kill switch, and now automated anomaly detection. That governance layer is the actual differentiator, and it's real, not a slide.

But the product's core promise — "turn a meeting into a reviewed pull request" — has a hole in the middle. The Dev stage, the one that writes code, still doesn't. It produces a placeholder diff string. Everything upstream (requirements, tickets, design doc) and downstream (review, merge, docs) can be made real; the actual code-generation step cannot yet. Any enterprise buyer's engineer will find this in the first working session. Lead with the governance story, not a "it writes your code" story, until that gap closes.

05

Pros and cons, for the room

Pros

  • Governance is real, not a slide.Least privilege, secrets vault, DLP, sandbox config, audit trail, kill switch, anomaly detection — all wired end-to-end, all tested.
  • Human stays in control.5 of 8 stages hard-stop for explicit approval; nothing merges or publishes unattended.
  • Real integrations, not demos.Jira, Confluence, and GitHub are driven through their actual hosted MCP servers — no scraped APIs, no brittle glue.
  • Architecture invites extension.Every connector has a clean mock/real split; adding a new system of record is a bounded, well-precedented change.
  • Tested discipline.66 tests, config-path verified for every real connector, before any credential is spent.

Cons

  • The headline feature is fake.Dev stage does not write code yet. This is the single biggest credibility risk in a sales conversation.
  • No enterprise auth.A pilot customer's security team will ask for SSO on day one; there isn't one.
  • Single-tenant, single-machine.No story yet for running this for more than one customer on shared infrastructure.
  • Unproven under load.Zero performance, concurrency, or failure-injection testing has been done.
  • Heavy manual setup.A pilot requires hand-configuring ~15 environment variables across 4 external systems.

08

What closes the gap to sellable

Highest priority

Real Dev-stage code generation

Wire Dev into an agentic claude-agent-sdk loop with real file-edit/bash tools, so it produces an actual diff instead of a placeholder — this is also what finally gives the existing sandbox settings a live consumer.

Required for any paid pilot

Real auth: SSO/OIDC + RBAC on the web UI

Replace the single shared token with per-user identity and role-scoped approval rights — table stakes for any security review.

Required before multi-customer

Deployment + data platform

Dockerize it, move run state off local JSON into a real database, add health checks and CI — the difference between "a repo you clone" and "a service you operate."

Strengthens the pitch

Observability + resilience

Metrics/tracing on top of the existing audit trail, plus retry/backoff on connector calls, so a flaky external API doesn't fail an entire run.
